    Help · reading the city
    
          
    what the metrics mean and how to analyse a codebase
    
        
    
        
      
    

      
    
        
    CodeCity turns a codebase into a 3D city. Every
        class or module is a building, every folder / package is a
        district, and the size and colour of a building encode software metrics.
        The metaphor comes from Wettel & Lanza, “Visualizing Software
        Systems as Cities” (2007).
    

        
    Metrics
    
        
    
          
    MetricFull nameMapped toWhat it tells you
    
          
            
    
              NOMNumber Of Methodsbuilding height
              How much behaviour a type has. Tall buildings are
              behaviour-heavy classes; a very tall one is usually doing too much.
            
    
            
    
              NOANumber Of Attributesbuilding footprint
              How much state a class holds. Wide bases mean
              data-heavy classes that keep a lot of fields.
            
    
            
    
              LOCLines Of Codebuilding colour
              Raw code size. Ramp: slate → teal → gold → crimson (low → high).
            
    
            
    
              DEPSDependenciesoptional dimension
              Imports + calls touching this building. High value = highly
              coupled. Roads on the ground draw these relationships.
            
    
              
        
    

        
    Mapping: the mapping dropdown chooses how a metric value
        becomes a size. boxplot (default) is the paper's approach: boundary
        values come from the data's quartiles/whiskers, so buildings take one of
        5 balanced sizes (very small → very tall) instead of a long tail of
        near-identical slabs. threshold uses 5 fixed bands, and
        linear maps the raw value continuously.
    

        
    On “NOC”
    
        
    NOC is a classic OO metric for Number Of Classes (and,
        in inheritance metrics, also Number Of Children). It is easy to
        confuse with NOA (Number Of Attributes) used here. This tool does
        not map NOC onto a building, because districts already group
        classes: the number of classes in a package is simply the number of
        buildings sitting on that district plate (see the district dropdown,
        which shows the per-district building count). If you need inheritance
        fan-out (Number Of Children), it is not modelled — the CodeGraph index
        exposes only one extends edge in this repo, so it would add
        colour without adding insight.
    

        
    How to read the city
    
        
      
          
    • Districts — the raised plates. The largest plates are the
          largest packages; a sprawling district is a package doing too much.
      • 
          
    • Tall (high NOM) — a class with many methods.
      • 
          
    • Wide / big footprint (high NOA) — a class holding a lot of state.
      • 
          
    • Warm/red colour (high LOC) — a big file/class.
      • 
          
    • Tall + red — the classic “God class” shape: many methods
          and lots of code. These are your first refactoring targets.
      • 
          
    • Streets — imports/calls between buildings, drawn on the ground.
          Roads (wide, yellow lane lines) carry the heaviest links,
          streets and alleys (narrow, white centre line) the rest.
          The number of people walking a street is how many connections it
          represents. Many streets leading into a building = high fan-in
          (widely used; changes are risky). Many leading out = high fan-out
          (it depends on everything).
      • 
        
    

        
    How to analyse a codebase with it
    
        
      
          
    1. Open a project: start with npx codecity-viewer,
          then choose a folder from the Project menu.
      2. 
          
    2. Survey districts first: the biggest plates reveal the
          architecture and where the mass of the code lives.
      3. 
          
    3. Find outliers: look for the tallest, widest and reddest
          buildings inside each district — that is where complexity hides.
      4. 
          
    4. Inspect one: click a building to see its file, LOC, NOM,
          NOA and dependency count, plus its members (methods/attributes) —
          click a member to highlight the building. Press copy path to
          jump to the source.
      5. 
          
    5. Study coupling: hover buildings and follow the streets. A
          cluster of mutually connected buildings is a tightly coupled module
          and a candidate to split.
      6. 
          
    6. Switch metrics: change height, footprint and
          colour in the left panel to hunt different smells — e.g. map
          dependencies onto height to expose coupling hotspots.
      7. 
          
    7. Focus: use search to fly to a class, and the
          district filter to isolate a package; toggle streets
          and grid to declutter.
      8. 
          
    8. Confirm in the source: metrics are a map, not a verdict —
          always open the file before acting.
      9.

    Metrics are exact when built from a CodeGraph
        index and estimates when built by the source scanner
        (--source scan), which approximates per-class methods,
        attributes and LOC. Python uses the standard-library parser;
        JS/TS and other languages use estimates from regexes.
